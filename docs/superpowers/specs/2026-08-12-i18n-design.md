# Lehaim v2 — Internationalisation (chantier 1 : interface)

Date : 2026-08-12
Statut : validé, prêt pour le plan d'implémentation

## But

Rendre l'app disponible en **français, anglais, espagnol, hébreu et russe**, et
faire en sorte que **toute fonctionnalité écrite après ce chantier soit traduite
sans effort supplémentaire** — cette seconde exigence pèse autant que la
première et détermine plusieurs choix ci-dessous.

## Périmètre

Sacha a demandé que « tout » soit traduit, contenu utilisateur compris. Les deux
familles relèvent de mécanismes incompatibles : l'interface se pré-calcule et se
commite, un message posté à 19 h ne le peut pas. D'où deux chantiers.

**Dans ce chantier :**

- les chaînes d'interface écrites en dur (~300–400, sur 50 pages)
- les catalogues de réponses de l'onboarding (`lib/onboarding.ts`)
- les messages WhatsApp générés (`lib/whatsapp.ts`, `lib/templates.ts`)
- les dates, durées et montants (`lib/format.ts`)

**Hors de ce chantier**, renvoyé au chantier 2 : le contenu écrit par les
utilisateurs (titres de Chabbat, fil de discussion, noms de missions). Il exige
une traduction à l'affichage, un cache et une politique de repli — un système à
part, qui s'appuiera sur les fondations posées ici.

## Décisions

| Sujet | Décision | Raison |
|---|---|---|
| Langue source | Français, dans le code | C'est l'existant ; aucune réécriture préalable |
| Sélection de la langue | Profil + cookie, **URL inchangée** | Évite de déplacer 50 pages sous `app/[locale]/` |
| Production des traductions | Claude Code en session, sur demande | Pas de clé d'API, pas de coût, diff git relisible |
| Bibliothèque | `next-intl` 4.13.6 | Seule à couvrir App Router + RSC + ICU ; `next: ^16.0.0` vérifié en peer dependency |

### Pourquoi ICU, et pas un `t()` maison

Le russe a **trois formes de pluriel** (1 / 2–4 / 5+, la règle repartant à chaque
dizaine), l'hébreu deux plus un duel. L'app affiche partout des « 3 invités
confirmés », « il reste 2 missions », « encore 4 questions ». Sans ICU, chaque
phrase de ce type devient une fonction manuelle par langue — du code qu'on croit
simple, qui se trompe sur les cas limites, et dont personne ici ne verra l'erreur
en russe. `next-intl` fournit aussi le formatage `Intl` des dates et des nombres,
ce qui règle `lib/format.ts` du même coup.

## Architecture

### Résolution de la langue

Une seule fonction serveur, `lib/i18n/locale.ts`, dans cet ordre :

1. cookie `NEXT_LOCALE` — choix explicite, prioritaire
2. colonne `profiles.locale` — suit la personne d'un appareil à l'autre
3. en-tête `Accept-Language` — couvre l'invité sans compte qui ouvre un lien WhatsApp
4. `fr` par défaut

Les étapes 3 et 4 sont ce qui permet à un invité russophone d'arriver dans sa
langue sans jamais avoir créé de compte.

```
LOCALES = ['fr', 'en', 'es', 'he', 'ru']
RTL_LOCALES = ['he']
DEFAULT_LOCALE = 'fr'
```

### Fichiers de messages

`messages/{fr,en,es,he,ru}.json`, découpés par domaine : `common`, `auth`,
`onboarding`, `survey`, `shabbat`, `missions`, `invitation`, `whatsapp`,
`settings`. Le français fait autorité sur la liste des clés.

Composants serveur : `getTranslations('onboarding')`.
Composants client : `useTranslations('onboarding')`, avec `NextIntlClientProvider`
posé dans le layout racine.

### Stockage du choix

Migration `0008_locale.sql` : `alter table public.profiles add column if not
exists locale text` avec une contrainte `check` sur les cinq valeurs — même
approche additive et nullable que `0007`.

Un sélecteur dans `/reglages` écrit le cookie **et** la colonne, via une server
action.

### RTL

`<html dir>` calculé depuis la langue résolue. Les 50 classes directionnelles
physiques relevées dans le code (`ml-`, `pl-`, `left-`, `text-left`, `border-l`,
`rounded-l`) passent en logiques (`ms-`, `ps-`, `start-`, `text-start`,
`border-s`, `rounded-s`). Tailwind v4 les résout selon `dir`, donc une seule
écriture couvre les deux sens.

Exceptions à forcer en `dir="ltr"` même en hébreu : le champ téléphone, les
adresses e-mail, et l'affichage des montants. Un numéro affiché en RTL devient
illisible.

### Polices

Relevé de couverture réelle, lu dans les données de `next/font` :

| Police | Rôle | Hébreu | Cyrillique |
|---|---|---|---|
| Fredoka | titres | ✅ | ❌ |
| Nunito | texte | ❌ | ✅ |

Aucune ne couvre les cinq langues. On garde les deux pour le latin et on
substitue **uniquement là où la couverture manque** :

- hébreu → **Assistant** pour le texte courant (humaniste, proche de Nunito)
- russe → **Rubik** pour les titres (arrondie, proche de Fredoka)

Mise en œuvre par surcharge des variables existantes dans `globals.css` :

```css
html[lang="he"] { --font-sans: var(--font-assistant); }
html[lang="ru"] { --font-display: var(--font-rubik); }
```

Aucun composant ne change : ils lisent déjà `--font-display` et `--font-sans`.

## Traduire les fonctionnalités futures

C'est l'exigence structurante. Trois mécanismes, du plus contraignant au plus
souple.

**1 · Parité des clés, vérifiée en CI.** `npm run i18n:check` compare les clés des
cinq fichiers et sort en code non nul en listant les manquantes et les orphelines.
Branché dans l'action GitHub, **un déploiement échoue si une langue est
incomplète**. C'est la garantie dure : on ne peut pas publier une fonctionnalité
à moitié traduite.

**2 · Détection du texte en dur.** Une règle ESLint signale les littéraux de texte
dans le JSX, pour attraper la chaîne oubliée *avant* qu'elle manque dans les
quatre autres langues. Si l'intégration en flat config s'avère fragile, on
retombe sur un script de détection maison lancé par le même `i18n:check` — la
garantie 1 reste intacte dans les deux cas.

**3 · Remplissage.** `npm run i18n:missing` sort les clés absentes avec leur texte
français. Je les traduis en session et j'écris les cinq fichiers ; le diff git
reste relisible langue par langue.

En pratique, écrire une fonctionnalité devient : rédiger en français dans
`messages/fr.json`, lancer `i18n:missing`, me demander la passe de traduction.

## Ordre d'implémentation

1. **Socle** — `next-intl`, résolution de la langue, migration `0008`, RTL,
   polices, sélecteur dans `/reglages`. Rien de visible ne change en français.
2. **Onboarding** — les 15 écrans les plus récents, en premier parce que ce sont
   les mieux connus et qu'ils servent de patron pour le reste.
3. **Le reste des écrans** — les 35 pages restantes.
4. **Formats et messages générés** — `lib/format.ts`, `lib/whatsapp.ts`,
   `lib/templates.ts`.
5. **Garde-fous** — `i18n:check`, `i18n:missing`, branchement CI.

Chaque étape est déployable seule : à tout moment le français fonctionne, et une
langue incomplète retombe sur le français plutôt que d'afficher une clé brute.

## Vérification

- `npm run build` et `npm run lint` verts à chaque étape.
- `i18n:check` vert sur les cinq langues.
- Parcours de l'onboarding relu dans le navigateur en français, en hébreu (mise
  en page RTL) et en russe (pluriels et police des titres).
- Contrôle que le champ téléphone reste en LTR en hébreu.

## Risques

| Risque | Traitement |
|---|---|
| Qualité de l'hébreu et du russe invérifiable par Sacha | Traductions commitées et relisibles ; un locuteur peut corriger le JSON sans toucher au code |
| Régression de mise en page en RTL | Conversion en classes logiques faite d'un bloc, puis relecture visuelle écran par écran |
| Chaîne oubliée dans une future fonctionnalité | `i18n:check` bloquant en CI |
| `lib/format.ts` réécrit | Couvert par le formatage `Intl` de `next-intl`, pas de logique de date maison conservée |
